## Идиома RAII <a id="raii"></a>

**Resource Acquisition Is Initialization (RAII)** - идиома, которая подразумевает, 
что получение ресурса совмещено с инициализацией объекта (обычно автоматической 
переменной на стеке или поля другого объекта).
Таким образом происходит связывание времени жизни объекта с владением ресурсом.

Получение ресурса происходит в конструкторе объекта, при инициализации, в начале 
времени жизни объекта, а освобождение ресурса в деструкторе при уничтожении объекта.
Такой подход предотвращает утечку ресурса, обеспечивая безопасность при исключениях:
при выбросе исключения стек раскручивается и деструкторы локальных объектов вызываются
автоматически.

В качестве ресурса может выступать динамическая память, файловый дескриптор, мьютекс 
(что-то, что выдано третьей стороной во временное пользование, и что нужно вернуть
по завершении использования).

Основная идея:

- Объект-владелец отвечает за жизненный цикл ресурса
- Ресурс захватывается в конструкторе объекта
- Ресурс освобождается в деструкторе объекта

Идиома RAII позволяет писать код без явных вызовов `delete` для выделенной памяти.

В стандартной библиотеке множество примеров реализации RAII:

- контейнеры, владеющие ресурсами (`std::vector`, `std::string`, `std::list`, ...)
- умные указатели `std::unique_ptr`, `std::shared_ptr`
- `std::lock_guard` для захвата мьютекса
- `std::ifstream`, `std::ofstream`, `std::fstream` для работы с файлами

В коде следует избегать явного управления ресурсами:

- вместо `new` - лучше использовать умные указатели и `std::make_unique`,
  `std::make_shared`
- вместо `new[]` - лучше использовать `std::vector` или другой подходящий контейнер

## Умные указатели <a id="smart_ptr"></a>

Умный указатель - класс-обертка над сырым указателем, который управляет ресурсом
(динамически выделенной памятью), и синтаксически может использоваться как обычный
указатель, то есть перегружает оператор разыменования `*` и оператор доступа по
указателю `->`.

Умные указатели призваны решать проблемы при работе с динамической памятью:

- Утечки памяти (memory leak) 
- Двойное удаление (double free)
- Использование неинициализированного указателя
- Висячий указатель (dangling pointer) и его использование
- Использование непарной версии оператора `delete`, `delete[]`

Простой **НЕ** рабочий вариант умного указателя:

```c++
using Resource = SomeClass;
class SmartPtr {
public:
    explicit SmartPtr(Resource* raw_ptr) : raw_ptr_(raw_ptr) {}
    ~SmartPtr() { delete raw_ptr_; }
    Resource& operator*() const { return *raw_ptr_; }
    Resource* operator->() const { return raw_ptr_; }
private:
    Resource* raw_ptr_ = nullptr;
};
```

Использование умного указателя подразумевает, что память выделяется непосредственно
при конструировании объекта:

```c++
SmartPtr student_ptr(new Student("Student", 18));
```
- память выделяется выражением `new` в аргументе и сразу передаётся в конструктор, после
  чего объект `student_ptr` владеет ресурсом и сам удалит объект при выходе из области
  видимости

**НЕ** следует создавать сырой указатель, как-то с ним работать, передавать в другие 
функции, классы в сыром виде, а потом только конструировать умный указатель, так как 
это может привести к проблемам (например, висячему указателю).

```c++
Student* student_raw_ptr = new Student("Student", 18);
// do something with raw pointer
SmartPtr student_ptr(student_raw_ptr);
```

Проблема данной реализации в том, что при вызове конструктора копирования, который
сгенерирует компилятор, произойдет копирование указателя и при выходе из области 
видимости будет ошибка double free из-за двойного удаления. 

```c++
{
    SmartPtr student_ptr(new Student("Student", 18));
    SmartPtr bad_copy_student_ptr(student_ptr);
} // UB double free :(
```

Поэтому необходимо определиться с семантикой владения. 

Можно выделить три семантики владения ресурсом:

- уникальное владение (один владелец, копирование невозможно, только перемещение)
- разделяемое владение (несколько владельцев, имеется счетчик ссылок на объект)
- не владеющее наблюдение (можно получить доступ к объекту, если он существует)

### Умные указатели STL (C++11) <a id="smart_ptr_stl"></a>

Умные указатели STL располагаются в заголовочном файле `<memory>`.

В стандартной библиотеке реализованы следующие умные указатели:

- `std::unique_ptr` - уникальное владение ресурсом
- `std::shared_ptr` - разделяемое владение ресурсом
- `std::weak_ptr` - слабая ссылка, ресурсом **НЕ** владеет (наблюдение)

Ранее существовал `std::auto_ptr`, но он _deprecated_ начиная с C++11, и
_removed_ в C++17. Им **НЕ** стоит пользоваться, так как в определенных ситуациях
имеет проблемы с управлением ресурсом.

## Умный указатель `std::unique_ptr` <a id="std_unique_ptr"></a>

В стандартной библиотеке есть умный указатель `std::unique_ptr`, который 
эксклюзивно (единолично, уникально) владеет переданным ему ресурсом. 

При создании умного указателя необходимо после имени класса указателя написать
тип данных в угловых скобках `<>`, с которым будет работать указатель.
Если нужен указатель на тип `int`, то пишется `int`, писать `int*` **НЕ** нужно:

```c++
std::unique_ptr<int> ptr;
```

По умолчанию конструируется указатель с `nullptr`, но такой случай мало интересен:

```c++
std::unique_ptr<int> ptr;
std::unique_ptr<int> ptr2{};
std::unique_ptr<int> ptr3{nullptr};
std::unique_ptr<int> ptr4 = {};
std::unique_ptr<int> ptr5 = nullptr;
```

Принято создавать объект при получении ресурса (согласно **RAII**):

```c++
std::unique_ptr<int> item{new int{18}};
```

Поскольку владение уникальное, то копирование указателя должно быть запрещено:
конструктор копирования и оператор присваивания копированием у класса удалены 
`= delete`.

```c++
SmartPtr(const SmartPtr&) = delete;
SmartPtr& operator=(const SmartPtr&) = delete;
```

Владение можно передать посредством перемещения:

```c++
std::unique_ptr<int> item{new int{18}};
std::unique_ptr<int> item_moved{std::move(item)}; // item = nullptr 
```

Конструктор перемещения в таком случае может выглядеть примерно так:

```c++
SmartPtr(SmartPtr&& other) noexcept : raw_ptr_(other.raw_ptr_) {
    other.raw_ptr_ = nullptr; // other must stay valid after move and not cause double free
}
```

Оператор присваивания перемещением корректно освобождает свой захваченный ресурс, 
перед перемещением (передачей владения) другого ресурса:

```c++
std::unique_ptr<int> item{new int{18}};
std::unique_ptr<int> item_moved{new int{19}};
item_moved = std::move(item); // item = nullptr 
```

Оператор присваивания перемещением в таком случае может выглядеть примерно так:

```c++
SmartPtr& operator=(SmartPtr&& other) noexcept {
    if (raw_ptr_ != other.raw_ptr_) { // self assignment check
        delete raw_ptr_; // delete current resource
        raw_ptr_ = other.raw_ptr_; // copy resource pointer from other
        other.raw_ptr_ = nullptr; // other must stay valid and not cause double free
    }
    return *this;
}
```

### Умный указатель на массив <a id="std_unique_ptr_to_array"></a>

Умный указатель способен работать также с массивом объектов, при этом выделяемая
память корректно освобождается с помощью парного оператора `delete[]`. 

Для корректности освобождения памяти следует правильно указать тип `int[]`:

```c++
std::unique_ptr<int[]> ptr{new int[10]{}};
```

**НО** считается более корректным подходом в таком случае использовать контейнер 
`std::vector<T>` вместо `std::unique_ptr<T[]>`.

### Методы и внешние функции <a id="std_unique_ptr_methods"></a>

Помимо специальных методов, умный указатель имеет методы и внешние функции:

- `get()` - получить сырой указатель
- `release()` - освобождает владение (возвращает указатель и становится `nullptr`)
- `reset(T* ptr = nullptr)` - удаляет старый объект и принимает владение новым
- `swap(std::unique_ptr<T>&)` - обменивается владеющими указателями
- `get_deleter()` - возвращает удалитель
- `explicit operator bool()` - приводит указатель к типу `bool`

Доступ к элементу в случае указателя на объект:

- Оператор `*` - разыменование указателя, возвращает ссылку
- Оператор `->` - доступ через указатель

Доступ к элементу в случае указателя на массив объектов:

- Оператор `[](size_t pos)` - доступ к элементу массива

Начиная с C++20 имеет оператор вывода в поток, который работает, как для сырого
указателя, выводит адрес:

- Оператор `<<` - перегрузка для вывода в поток адреса сырого указателя

Внешние функции:

- Операторы сравнения - сравнивают сырые указатели (адреса) 
- `std::make_unique` (C++14) - функция для создания умного указателя
- `std::make_unique_for_overwrite` (C++20) - функция для создания умного указателя
  с инициализацией по умолчанию
- `std::swap` - внешняя функция для работы в алгоритмах
- `std::hash` - хэш-функция для умного указателя

### Передача в функцию <a id="std_unique_ptr_func"></a>

Обычно для передачи в функцию принято использовать `*` и передавать ссылку, или
`get` и передавать сырой указатель, если известно, что функция ничего не делает
с указателем.

- `func(SomeClass* ptr)` - не передает владение, но объекта может не существовать
- `func(const SomeClass& obj)` - не передает владение, объект всегда существует

Функция может ожидать непосредственно `std::unique_ptr<SomeClass>`:

- `func(std::unique_ptr<SomeClass> ptr)` - передача владения, при вызове 
  явно передается владение `func(std::move(ptr))`
- `func(std::unique_ptr<SomeClass>& ptr)` - может изменить или освободить переданный
  умный указатель, например `std::swap` или метод `swap`
- `func(const std::unique_ptr<SomeClass>& ptr)` - несколько странно и вводит в
  заблуждение, `const` относится только к указателю, лучше передавать объект

### Функция `std::make_unique` (C++14) <a id="std_make_unique"></a>

Создание объекта `std::unique_ptr` имеет ряд неудобств:

- Необходимо выделять память с помощью `new` явно
- Необходимо дважды писать тип: при выделении памяти и в качестве шаблонного 
  параметра класса (а хочется использовать `auto`)
- Можно выделить память ранее, получить сырой указатель и использовать его даже
  после передачи в `std::unique_ptr` 
- Можно удалить память по сырому указателю, несмотря на передачу владения
- Нет гарантии безопасности относительно исключений при создании умного указателя 
  непосредственно в аргументах функции (до C++17)

Последняя проблема была самой важной. При создании умного указателя непосредственно 
в аргументах функции до C++17 была возможна утечка памяти, поскольку порядок
конструирования аргументов **НЕ** определен и может возникнуть ситуация, когда память
выделилась, но ещё не была помещена в умный указатель, и началось конструирование
другого объекта при котором возникла исключительная ситуация (выброшено исключение). 
В таком случае вызов функции закончится с ошибкой и выделенная память **НЕ** будет
освобождена.

```c++
void Func(std::unique_ptr<SomeClass> ptr, OtherClass obj);
OtherClass OtherThrowFunction();

Func(std::unique_ptr<SomeClass>(new SomeClass()), OtherThrowFunction());
```
- компилятор может сначала выделить память для `SomeClass`, а потом выполнить
  `OtherThrowFunction()` и только потом создать `std::unique_ptr<SomeClass>`

```c++
void Func(std::unique_ptr<SomeClass> ptr_one, std::unique_ptr<SomeClass> ptr_two);

Func(std::unique_ptr<SomeClass>(new SomeClass()), 
    std::unique_ptr<SomeClass>(new SomeClass()));
```
- компилятор может сначала выделить память для каждого объекта `SomeClass`, и только 
  потом создавать `std::unique_ptr<SomeClass>`, тогда в случае исключения в `SomeClass`
  один из объектов может утечь

Начиная с C++17 инициализация каждого параметра, включая все её побочные эффекты,
выполняется целиком, без чередования с другими параметрами. Поэтому `new SomeClass()` и 
конструктор `std::unique_ptr` для одного аргумента уже не могут разорваться вычислением
другого аргумента, и описанная утечка невозможна. Порядок вычисления аргументов 
по-прежнему **НЕ** определён.

В языке C++14 введена шаблонная функция `std::make_unique` (фабрика), которая лишена 
данных проблем. Функция `std::make_unique` принимает в качестве шаблонного параметра
тип, а в качестве аргументов принимает параметры для конструкторов данного типа, и
возвращает умный указатель. Это позволяет **НЕ** вызывать `new` явно, **НЕ** писать
дважды тип, **НЕ** иметь в коде сырой указатель, гарантировать безопасность при 
исключениях.

```c++
auto ptr = std::make_unique<SomeClass>(arg, other_arg);
```

Начиная с C++14 создавать умный указатель рекомендуется именно таким образом.
Исключением из рекомендации является необходимость нестандартного удалителя.

Также есть версия `std::make_unique_for_overwrite` (C++20). Она создаёт объект
_инициализацией по умолчанию_ (`new T`), а `std::make_unique` - _инициализацией
значением_ (`new T()`). Для классов конструктор по умолчанию вызывается в обоих
случаях, а объекты тривиальных типов (`int`, `double`, массивы из них) при
`_for_overwrite` остаются неинициализированными. Выигрыш есть только для
тривиальных типов, когда память всё равно будет сразу заполнена:

```c++
auto zeros = std::make_unique<char[]>(size);                  // filled with '\0'
auto buffer = std::make_unique_for_overwrite<char[]>(size);   // not initialized
```

Следует отметить, что `std::make_unique` не принимает нестандартный `Deleter`,
в таких случаях необходимо писать свою шаблонную функцию или создавать
`std::unique_ptr` конструктором, передавая удалитель.

### Нестандартный _Deleter_ `std::unique_ptr` <a id="std_unique_ptr_deleter"></a>

Помимо типа объекта `std::unique_ptr` имеет второй шаблонный параметр в `<>`.
Вторым параметром в шаблон передается тип удалителя _Deleter_, а в аргументы 
непосредственно функция или функциональный объект.

По умолчанию указан удалитель `std::default_delete<T>`, который вызывает 
`delete raw_ptr_` или `delete[] raw_ptr_` для массива.

Таким образом, для корректной работы класса `std::unique_ptr` с другими
ресурсами, необходимо передать удалитель, который будет корректно освобождать
ресурсы.

Например, при использовании функций языка C, когда необходимо вызывать `std::free`

```c++
std::unique_ptr<int, decltype(&std::free)> ptr(
    static_cast<int*>(std::malloc(sizeof(int))), 
    std::free);
```
- формально брать адрес функции стандартной библиотеки нельзя (C++20), если она
  **НЕ** помечена как _addressable_, а `std::free` к таким не относится (правило
  _addressing restriction_). Надёжнее использовать функтор

В целях логирования передать свой удалитель:

```c++
struct FreeDeleter {
    void operator()(void* ptr) const {
        std::cerr << "free() called\n";
        std::free(ptr);
    }
};

std::unique_ptr<int, FreeDeleter> ptr(static_cast<int*>(std::malloc(sizeof(int))));
std::unique_ptr<int, FreeDeleter> ptr_explicit_deleter(
    static_cast<int*>(std::malloc(sizeof(int))),
    FreeDeleter{});
```
- если удалитель имеет конструктор по умолчанию, то компилятор способен сам его создать 
  и нет необходимости передавать удалитель вторым аргументом

Если умный указатель используется не для выделения памяти, а для файла языка C (`FILE*`):

```c++
struct FileCloser {
    void operator()(FILE* file) const {
        std::cerr << "Closing file\n";
        std::fclose(file);
    }
};

std::unique_ptr<FILE, FileCloser> p2(std::fopen("test.txt", "r"));
```
- проверка на `nullptr` в удалителе не нужна: деструктор `std::unique_ptr` вызывает
  удалитель, только если указатель не нулевой
- для этих нужд в C++ уже есть RAII-обертка `std::fstream`

Нестандартный удалитель нужен и в других случаях: память выделена пользовательским
аллокатором, открыт сокет или получен другой ресурс со своей функцией освобождения.

Также удалитель может хранить состояние (поля).

### Эффективность `std::unique_ptr` <a id="std_unique_ptr_performance"></a>

Важно понимать, что `std::unique_ptr` очень легковесный класс-обертка над сырым
указателем и его использование вместо сырого указателя практически **НЕ** замедляет
выполнение кода и дает множество преимуществ.

Размер класса можно получить, используя оператор `sizeof`. Со стандартным удалителем
или удалителем без полей (функтор, лямбда без захвата) размер равен размеру указателя:
8 байт на 64-разрядной платформе. С указателем на функцию в качестве удалителя -
16 байт.

Поэтому, если есть возможность использовать `std::unique_ptr` среди прочих умных
указателей, следует выбрать его, так как он практически **НЕ** имеет оверхеда
(дополнительных накладных расходов) по производительности и по памяти.

Размер может увеличиваться, если принимается нестандартный _Deleter_, который
может хранить состояние.

## Умный указатель `std::shared_ptr` <a id="std_shared_ptr"></a>

В стандартной библиотеке есть умный указатель `std::shared_ptr`, который
реализует разделяемое (совместное) владение динамически выделенным ресурсом.

Несколько экземпляров `std::shared_ptr` могут владеть одним и тем же объектом.

Данный указатель должен знать, сколько имеется ссылок на конкретный объект,
которым он владеет, чтобы при выходе из области видимости не удалять 
выделенную память (освобождать ресурс) преждевременно. 

При выходе указателя из области видимости уменьшается счётчик ссылок. 
Освобождение ресурса происходит только тогда, когда из области видимости 
вышел последний указатель на объект (счетчик ссылок стал равным нулю).

Умный указатель `std::shared_ptr` устроен сложнее. Внутри хранится не только 
указатель на объект, но и указатель на блок управления (control block), который
естественно также выделяется в динамической памяти. Блок управления хранит
сразу два счетчика, счетчик сильных ссылок и счетчик слабых ссылок.

У данного указателя имеются специальные методы для копирования, при вызове
которых происходит увеличение счетчика ссылок и простое копирование указателей.

### Умный указатель на массив <a id="std_shared_ptr_to_array"></a>

До C++17 умный указатель не поддерживал работу с массивами по умолчанию.

Для корректности освобождения памяти массива необходимо передать пользовательский
удалитель, работающий с массивом, вторым аргументом в конструктор. Удалитель
у `shared_ptr` не является частью типа и хранится в блоке управления.

Начиная с C++17 появилась поддержка массивов и возможность обращения
к элементу по индексу `[]`. Теперь по умолчанию вызывается корректный
удалитель `delete raw_ptr_` или `delete[] raw_ptr_` для массивов.

```c++
std::shared_ptr<int[]> arr(new int[10]{}); // C++17
std::shared_ptr<int> old(new int[10]{}, std::default_delete<int[]>()); // before C++17
```

### Методы и внешние функции <a id="std_shared_ptr_methods"></a>

Помимо специальных методов, умный указатель имеет методы и внешние функции:

- `get()` - получить сырой указатель
- `reset()` и `reset(T* ptr)` - удаляет старый объект и принимает владение новым,
  также имеет версии принимающие Deleter и Allocator
- `swap(std::shared_ptr<T>&)` - обменивается владеющими указателями
- `use_count()` - возвращает количество владельцев (в многопоточной программе
  значение приблизительное, для логики его **НЕ** используют)
- `explicit operator bool()` - приводит указатель к типу `bool`

Доступ к элементу в случае указателя на объект:

- Оператор `*` - разыменование указателя, возвращает ссылку
- Оператор `->` - доступ через указатель

Доступ к элементу в случае указателя на массив объектов:

- Оператор `[](size_t pos)` (C++17) - доступ к элементу массива

Имеет оператор вывода в поток, который работает, как для сырого указателя, 
выводит адрес:

- Оператор `<<` - перегрузка для вывода в поток адреса сырого указателя

Внешние функции:

- Операторы сравнения - сравнивают сырые указатели (адреса)
- `std::make_shared` (C++11) - функция для создания умного указателя
- `std::make_shared_for_overwrite` (C++20) - функция для создания умного указателя
  с инициализацией по умолчанию
- `std::swap` - внешняя функция для работы в алгоритмах
- `std::hash` - хэш-функция для умного указателя
- `std::get_deleter` - возвращает указатель на удалитель
- `std::atomic<std::shared_ptr<T>>` (C++20) - поддержка атомарного доступа к 
  самому умному указателю

### Передача в функцию <a id="std_shared_ptr_func"></a>

Можно использовать `*` и передавать ссылку, или `get` и передавать сырой указатель, 
если известно, что функция **НЕ** сохраняет указатель или **НЕ** удаляет память или 
**НЕ** меняет указатель. Также важно гарантировать, что объект будет жив до
окончания работы функции. Наиболее производительный вариант работы.

- `func(SomeClass* ptr)` - не передает владение, но объекта может не существовать
- `func(const SomeClass& obj)` - не передает владение, объект всегда существует

Функция может ожидать непосредственно `std::shared_ptr<SomeClass>`:

- `func(std::shared_ptr<SomeClass> ptr)` - разделение владения, увеличивает счетчик 
  ссылок. Используется в асинхронных операциях, когда нужно гарантировать, что объект
  будет жив. Можно передать владение, используя `std::move(shared)` при передаче в
  функцию. 
- `func(std::shared_ptr<SomeClass>& ptr)` - может изменить или освободить переданный
  умный указатель, например `std::swap` или метод `swap`, возврат через параметр
- `func(const std::shared_ptr<SomeClass>& ptr)` - наблюдение за объектом, счетчик 
  ссылок не увеличивается, требует проверки на `nullptr` перед использованием. Может
  быть опасно и приводить к разыменованию `nullptr`
- `func(std::shared_ptr<SomeClass>&& ptr)` - функция _может_ забрать владение
  (`std::move(ptr)` внутри), но не обязана

### Функция `std::make_shared` <a id="std_make_shared"></a>

В отличие от `std::make_unique` (C++14), `std::make_shared` существует,
начиная с C++11. 

Функция `std::make_shared` принимает в качестве шаблонного параметра тип, 
а в качестве аргументов принимает параметры для конструкторов данного типа, 
и возвращает умный указатель. 

Рекомендуется также создавать объект с помощью `std::make_shared`. Помимо решения
ранее описанных проблем, функция `std::make_shared` выделяет память под объект и под
блок управления единым фрагментом, в отличие от обычного создания умного указателя, 
при котором объект и блок управления могут находиться в памяти не рядом. Такой
подход более оптимален с точки зрения производительности (адреса находятся близко) и
меньше фрагментация памяти.

Таким образом `std::make_shared` имеет следующие преимущества:

- Одно выделение памяти вместо двух
- Лучшая локальность данных (объекта и блока управления)
- Гарантия безопасности при исключениях

**НО** объект и блок управления теперь - одно выделение памяти. Деструктор объекта
вызывается, когда обнулится счётчик сильных ссылок, а вся память (и объекта, и
блока) освобождается, только когда обнулится и счётчик слабых ссылок. Если объект
большой и на него долго остаются `std::weak_ptr`, память под объект остаётся
занятой.

Важным отличием `std::make_shared` от `std::make_unique` является то, что 
до C++20 данная функция **НЕ** могла работать с массивами (поддержка массивов 
в умный указатель `std::shared_ptr` была добавлена только в C++17).

Также есть версия `std::make_shared_for_overwrite` (C++20) с инициализацией по
умолчанию, аналогично `std::make_unique_for_overwrite`.

### Нестандартный _Deleter_ `std::shared_ptr` <a id="std_shared_ptr_deleter"></a>

В отличие от `std::unique_ptr` умный указатель `std::shared_ptr` **НЕ** имеет 
второго шаблонного параметра для удалителя, то есть он **НЕ** является частью типа 
умного указателя. Удалитель можно передать аргументом при конструировании объекта.
Удалитель хранится в блоке управления со стиранием типа (type erasure).

По умолчанию при удалении вызывается `delete raw_ptr_` до C++17, начиная
с C++17 также поддерживается версия для массивов, которая автоматически
вызывает `delete[] raw_ptr_` для массивов.

Для корректной работы класса `std::shared_ptr` с другими ресурсами, необходимо
передать удалитель, который будет корректно освобождать ресурсы.

В распространённых реализациях освобождение ресурса через блок управления всегда 
идёт через виртуальную функцию, со стандартным удалителем тоже.

### Создание `std::shared_ptr` из `std::unique_ptr` <a id="std_shared_ptr_from_unique"></a>

Можно создавать `std::shared_ptr` из `std::unique_ptr`, поскольку передается
владение. При этом выделяется только блок управления, объект уже существует, так что
выделений памяти два, как без `std::make_shared`. Удалитель `std::unique_ptr`
переносится в блок управления. Чтобы осуществить такую передачу, необходимо обернуть
указатель `std::unique_ptr` в `std::move`:

```c++
auto unique = std::make_unique<int>(5);
std::shared_ptr<int> shared = std::move(unique); // unique == nullptr
```
- поэтому фабричной функции удобно возвращать `std::unique_ptr`, получить
  разделяемое владение легко в вызывающем коде 

**НЕЛЬЗЯ** создавать `std::unique_ptr` из `std::shared_ptr`, поскольку есть
блок управления, даже если владелец один, блок управления мог создаваться
вместе с объектом в одном фрагменте памяти. Метода `release()` нет у
`std::shared_ptr`, поскольку он не может отказаться от владения, так как
объектом могут владеть и другие умные указатели.

### Эффективность `std::shared_ptr` <a id="std_shared_ptr_performance"></a>

Важно понимать, что `std::shared_ptr` имеет значительно большие накладные расходы
на использование, чем `std::unique_ptr`. Поэтому его использование должно быть
только там, где действительно необходимо совместное владение.

Указатель на объект хранится прямо в `std::shared_ptr`, поэтому разыменование
стоит столько же, сколько у сырого указателя: блок управления при этом **НЕ**
используется. Расходы появляются при копировании, присваивании и уничтожении:
счётчики в блоке управления изменяются атомарными операциями, а это медленнее, чем
изменение обычных переменных, особенно когда один и тот же объект копируют из
разных потоков. Поэтому без необходимости `std::shared_ptr` по значению **НЕ**
передают.

Атомарность нужна для безопасного разделяемого владения из разных потоков.
Потокобезопасно только изменение счётчиков: одновременная запись в один и тот же
объект `std::shared_ptr` или в управляемый объект из разных потоков - гонка данных.

Размер класса можно получить, используя оператор `sizeof`. Класс имеет размер 
16 байт, то есть совпадает с размером двух указателей 8 байт для 64-разрядной
платформы.

Размер контрольного блока может увеличиваться, если принимается нестандартный 
_Deleter_, который может хранить состояние.

### Проблема циклических ссылок `std::shared_ptr` <a id="std_shared_ptr_cyclic_ref"></a>

Иногда использование умного указателя `std::shared_ptr` может приводить к утечкам
памяти. Эта проблема называется проблемой циклических (перекрестных) ссылок.
Проблема возникает, когда два объекта какого-то класса, хранят умные указатели 
`std::shared_ptr` друг на друга. 

В такой ситуации при выходе из области видимости каждого из объектов не произойдет
обнуления счетчика ссылок, поскольку остается объект, который имеет ссылку. 
Следовательно, выделенная память не освободится, произойдет утечка.

```c++
struct Dog; // forward declaration
struct Priest {
    std::shared_ptr<Dog> dog;
};
struct Dog {
    std::shared_ptr<Priest> owner;
};

void problem_cyclic_ref() {
    auto priest_ptr = std::make_shared<Priest>(); // priest_shared_count = 1
    auto dog_ptr = std::make_shared<Dog>(); // dog_shared_count = 1
    
    priest_ptr->dog = dog_ptr; // dog_shared_count = 2
    dog_ptr->owner = priest_ptr; // priest_shared_count = 2
} // dtors for Dog and Priest not called because counters = 1 (memory leak)
```

Важно понимать, что это **НЕ** обязательно прямая ссылка владения, куда чаще
это может происходить в списке или в графе с циклами через несколько элементов.

Для решения этой проблемы как раз существует слабый указатель `std::weak_ptr`.
Достаточно, чтобы одна из сторон цикла **НЕ** владела другой:

```c++
// fixed version of Dog
struct Dog {
    std::weak_ptr<Priest> owner; // does not own: no cycle
};
```

## Умный указатель `std::weak_ptr` <a id="std_weak_ptr"></a>

Для решения проблемы циклических ссылок в стандартной библиотеке имеется
слабый (не владеющий) указатель `std::weak_ptr`. Умный указатель `std::weak_ptr`
является наблюдателем за владеющим указателем `std::shared_ptr`.

Указатель `std::weak_ptr` позволяет безопасно узнать, существует ли объект, 
на который он ссылается, и получить к нему временный доступ, если объект 
всё ещё жив. Наличие слабой ссылки не продлевает объекту жизнь. Он будет удалён, 
как только на него перестанут ссылаться `std::shared_ptr`.

Блок управления, создаваемый `std::shared_ptr` имеет не только счетчик владеющих
ссылок, но также счетчик слабых ссылок, что позволяет знать, когда можно
освобождать память, выделенную непосредственно под блок управления.

Указатель `std::weak_ptr` создается из указателя `std::shared_ptr` или
из другого `std::weak_ptr`. При этом увеличивается счетчик слабых ссылок 
в блоке управления.

Указатель `std::weak_ptr` хранит аналогично `std::shared_ptr` два указателя,
на данные и на блок управления.

### Методы и внешние функции <a id="std_weak_ptr_methods"></a>

Помимо специальных методов, умный указатель имеет методы и внешние функции:

- `reset()` - убирает ссылку на владеющий объект
- `swap(std::weak_ptr<T>&)` - обменивается указателями на наблюдаемый объект
- `use_count()` - возвращает количество владельцев исходного объекта
- `expired()` - проверяет, истекло ли время жизни исходного объекта `use_count() == 0`
- `lock()` - создает владеющий указатель `std::shared_ptr` на объект, если 
  он ещё жив или пустой `std::shared_ptr` для удаленного объекта

```c++
if (auto sp = weak.lock()) {
    // object is alive while sp exists
}
```
- проверка `if (!weak.expired()) weak.lock()->...` в многопоточной программе
  небезопасна: объект может быть удалён между вызовами `expired()` и `lock()`

Внешние функции:

- `std::swap` - внешняя функция для работы в алгоритмах
- `std::atomic<std::weak_ptr<T>>` (C++20) - атомарный доступ к самому умному указателю

### Передача в функцию <a id="std_weak_ptr_func"></a>

Функция принимает `std::weak_ptr<SomeClass>`:

- `func(std::weak_ptr<SomeClass> ptr)` - создание копии, увеличивает счетчик слабых
  ссылок.
- `func(std::weak_ptr<SomeClass>& ptr)` - может изменить или освободить переданный
  умный указатель, например `std::swap` или метод `swap`
- `func(const std::weak_ptr<SomeClass>& ptr)` - счетчик слабых ссылок не увеличивается
- `func(std::weak_ptr<SomeClass>&& ptr)` - функция может забрать `std::weak_ptr`,
  исходный станет пустым (`expired() == true`), только если функция переместит из него

## Потоки ввода-вывода <a id="streams"></a>

В первой лекции рассматривались стандартные потоки `std::cin`, `std::cout`, `std::cerr`,
`std::clog`, операторы `<<` и `>>`, разница между `std::endl` и `'\n'`, ускорение
ввода-вывода и перенаправление потоков через консоль. 

Теперь разберём, как потоки устроены: из каких классов состоят, как сообщают об ошибках
и как форматируют данные. Всё это одинаково работает для консоли, файлов и строк.

### Иерархия классов потоков <a id="streams_hierarchy"></a>

Потоки стандартной библиотеки образуют иерархию классов
([Input/output library](https://en.cppreference.com/w/cpp/io.html)):

```txt
std::ios_base
└── std::ios
    ├── std::istream ──── std::ifstream, std::istringstream
    ├── std::ostream ──── std::ofstream, std::ostringstream
    └── std::iostream ─── std::fstream, std::stringstream
        (наследник std::istream и std::ostream)
```
- `std::ios_base` - флаги форматирования, режимы открытия, типы для позиционирования
- `std::ios` - состояние потока и указатель на буфер
- `std::istream` - ввод: `>>`, `get`, `getline`, `read`, `seekg`
- `std::ostream` - вывод: `<<`, `put`, `write`, `flush`, `seekp`
- `std::iostream` - ввод и вывод
- `std::cin` имеет тип `std::istream`
- `std::cout`, `std::cerr`, `std::clog` имеют тип `std::ostream`

Поток отвечает за форматирование (число `42` → символы `'4'`, `'2'`), а хранит и
передаёт символы **буфер потока**: `std::streambuf` и его наследники `std::filebuf`,
`std::stringbuf`. Получить буфер можно методом `rdbuf()`.

Главное следствие наследования: функция, которая принимает `std::istream&` или
`std::ostream&`, работает с **любым** потоком соответствующего направления.

```c++
std::vector<Record> ReadRecords(std::istream& in);

ReadRecords(std::cin);                      // консоль
std::ifstream file("records.txt");
ReadRecords(file);                          // файл
std::istringstream text("Ivan;25;4.5\n");
ReadRecords(text);                          // строка, удобно для тестов
```

Потоки **НЕ** копируются: копирующие конструктор и присваивание удалены. Поэтому
поток передаётся в функцию по ссылке. Файловые и строковые потоки можно перемещать
(C++11).

### Состояние потока <a id="stream_state"></a>

Каждый поток хранит **состояние** - набор флагов типа
[`std::ios_base::iostate`](https://en.cppreference.com/w/cpp/io/ios_base/iostate.html):

- `goodbit` - ошибок нет (значение `0`)
- `eofbit` - при вводе достигнут конец данных
- `failbit` - операция не удалась: не удалось прочитать ожидаемые символы или вывести
  нужные
- `badbit` - поток повреждён, например ошибка чтения с диска

Методы для работы с состоянием:

- `good()` - флаги не установлены
- `eof()` - установлен `eofbit`
- `fail()` - установлен `failbit` **или** `badbit`
- `bad()` - установлен `badbit`
- `explicit operator bool()` - то же, что `!fail()`
- `operator!()` - то же, что `fail()`
- `rdstate()` - получить все флаги
- `setstate(flag)` - добавить флаг
- `clear(flags = goodbit)` - **заменить** состояние, по умолчанию сбросить все флаги

Оператор `>>` возвращает поток, а поток приводится к `bool`, поэтому чтение и
проверку записывают вместе:

```c++
int value = 0;
if (std::cin >> value) {
    // read is successful
}
while (std::cin >> value) {
    // read until error or end of input
}
```

Изменение состояния при чтении:

```c++
std::istringstream in("42 abc 18");
int x = -1;

in >> x;           // x = 42, good
in >> x;           // "abc" is not a number: x = 0, fail
in >> x;           // stream in fail state: nothing is read, x = 0
in.clear();        // reset state

std::string word;
in >> word;        // word = "abc"
in >> x;           // x = 18, eof = 1, fail = 0
in >> x;           // nothing to read: eof = 1, fail = 1, x = 18
```
- пока установлен `failbit` или `badbit`, все последующие операции ввода ничего
  **НЕ** делают, поэтому после ошибки поток нужно сбросить методом `clear()`
- при неудачном преобразовании числа в переменную записывается `0`, при выходе за
  диапазон типа - наибольшее или наименьшее значение, в обоих случаях
  устанавливается `failbit` (C++11).
- если поток уже был в состоянии ошибки или данных нет совсем, преобразование не
  выполняется и переменная **НЕ** меняется (`x = 18` в последней строке)
- `eofbit` может быть установлен при **успешном** чтении: число `18` стоит в конце
  данных, и, чтобы понять, что число закончилось, поток дошёл до конца
- `clear()` сбрасывает только флаги, данные из потока **НЕ** удаляются

**ВАЖНО**: `eof()` сообщает, что конец данных уже был достигнут предыдущей операцией,
а **НЕ** что следующее чтение будет неудачным. Поэтому проверять нужно результат
чтения, а не `eof()` перед чтением.

### Обработка ошибок ввода <a id="stream_input_errors"></a>

Если пользователь ввёл не число, поток переходит в состояние ошибки, а неверные
символы остаются в потоке. Чтобы продолжить, нужно сбросить состояние и выбросить
неверный ввод:

```c++
bool ReadInt(std::istream& in, std::ostream& out, int& value) {
    while (!(in >> value)) {
        if (in.eof()) {
            return false;
        }
        in.clear();                                                   // reset failbit
        in.ignore(std::numeric_limits<std::streamsize>::max(), '\n'); // skip line
        out << "Not a number, try again: ";
    }
    return true;
}
```
- чаще используют возврат по значению переменной и исключения при невозможности или
  `std::optional<int>`
- `ignore(n, del)` пропускает до `n` символов или до символа `del` включительно
- значение `std::numeric_limits<std::streamsize>::max()` в качестве `n` означает без
  ограничения
- без проверки `eof()` при закрытом вводе (Ctrl+D в Linux, Ctrl+Z в Windows)
  цикл станет бесконечным

Оператор `>>` читает число до первого неподходящего символа и **НЕ** проверяет, что
строка закончилась: из ввода `12x` будет прочитано `12`, а `x` останется в потоке и
сломает следующее чтение.

### Манипуляторы и форматирование <a id="stream_manipulators"></a>

_Манипулятор_ - объект или функция, которую выводят в поток (или вводят из потока),
чтобы изменить его настройки, например `std::endl`, `std::flush`, `std::ws`
([io manipulators](https://en.cppreference.com/w/cpp/io/manip.html)). Манипуляторы с
аргументами объявлены в `<iomanip>`, остальные - в `<ios>`.

- `std::boolalpha`, `std::noboolalpha` - `bool` как `true`/`false` или `1`/`0`
- `std::dec`, `std::hex`, `std::oct` - система счисления целых (вывод и ввод)
- `std::showbase`, `std::noshowbase` - префикс `0x`, `0`
- `std::uppercase`, `std::nouppercase` - заглавные буквы: `0XFF`, `1E+10` 
- `std::showpos`, `std::noshowpos` - знак `+` у положительных чисел
- `std::fixed`, `std::scientific` - формат с фиксированной точкой или экспоненциальный
- `std::hexfloat`, `std::defaultfloat` - шестнадцатеричный, формат по умолчанию (C++11)
- `std::left`, `std::right`, `std::internal` - выравнивание в поле ширины
- `std::skipws`, `std::noskipws` - пропускать ли пробельные символы при вводе `>>`
- `std::setprecision(n)` - точность чисел с плавающей точкой
- `std::setw(n)` - ширина поля, **только для следующего** вывода
- `std::setfill(c)` - символ заполнения
- `std::quoted(s)` - строка в кавычках с экранированием (C++14)

```c++
std::cout << true << ' ' << std::boolalpha << true << '\n';            // 1 true
std::cout << 255 << ' ' << std::hex << 255 << ' '
    << std::showbase << 255 << '\n';                                   // 255 ff 0xff
std::cout << std::dec << std::noshowbase;
std::cout << 3.14159265 << ' '                                         // 3.14159
    << std::setprecision(3) << 3.14159265 << ' '                       // 3.14
    << std::fixed << 3.14159265 << '\n'                                // 3.142
    << std::scientific << 3.14159265 << '\n';                          // 3.142e+00
std::cout << '[' << std::setw(6) << 42 << "][" << 42 << "]\n";         // [    42][42]
std::cout << '[' << std::setfill('0') << std::setw(6) << 42 << "]\n";  // [000042]
```
- без `std::fixed` точность - общее число значащих цифр, с ним - число цифр после
  точки; по умолчанию точность `6`
- все настройки, кроме ширины, сохраняются до явного изменения; ширина сбрасывается
  после каждого вывода

Изменённые настройки `std::cout` влияют на весь последующий вывод программы, в том
числе в чужом коде. Если функция меняет форматирование, его можно предварительно
сохранить, а после восстановить посредством метода `copyfmt()`:

```c++
std::ios saved(nullptr);
saved.copyfmt(std::cout);                                // save format
std::cout << std::hex << std::uppercase << 3054 << '\n'; // BEE
std::cout.copyfmt(saved);                                // restore format
std::cout << 3054 << '\n';                               // 3054
```
- `copyfmt` копирует флаги, точность, ширину и символ заполнения
- можно сохранять по отдельности: `flags()`, `precision()`, `fill()`

В C++20 появилась функция форматирования `std::format` (`<format>`), а в C++23 -
`std::print` и `std::println` (`<print>`). Они удобнее манипуляторов и **НЕ** меняют
состояние потока, но в этом разделе рассматриваются только потоки.

## Файловые потоки `<fstream>` <a id="fstream"></a>

Для работы с файлами в заголовочном файле `<fstream>` есть три класса:

- `std::ifstream` - чтение из файла (наследник `std::istream`)
- `std::ofstream` - запись в файл (наследник `std::ostream`)
- `std::fstream` - чтение и запись (наследник `std::iostream`)

Файловый поток - это RAII-обёртка над открытым файлом: файл открывается в
конструкторе и закрывается в деструкторе. 

Всё, что известно о `std::cin` и `std::cout`, работает и с файловыми потоками.

### Открытие и закрытие файла <a id="fstream_open"></a>

Файл можно открыть в конструкторе или позже методом `open`:

```c++
std::ifstream in("data.txt");      // open for reading

std::ofstream out;                 // not associated with a file
out.open("result.txt");            // open for writing
```
- путь можно передать как `const char*`, `std::string` (C++11) или
  `std::filesystem::path` (C++17)
- `is_open()` - открыт ли файл
- `close()` - закрыть файл; после этого тем же объектом можно открыть другой файл

Если файл уже открыт, `open()` завершится ошибкой (`failbit`), сначала нужен `close()`.
При успешном `open()` состояние потока сбрасывается (`clear()`, C++11), поэтому объект 
можно переиспользовать после ошибки.

**ВАЖНО**: при неудачном открытии исключение **НЕ** выбрасывается, а устанавливается
`failbit`. Все последующие операции молча ничего не делают. Поэтому после открытия
файла его нужно проверить:

```c++
void ReadText(const std::filesystem::path& path) {
    std::ifstream in(path);
    if (!in.is_open()) {     // or if (!in)
        return;
    }
    // ...
}
```
- причину ошибки (нет файла, нет прав) стандартная библиотека **НЕ** сообщает;
  проверить существование файла можно функцией `std::filesystem::exists` (C++17)

**ВАЖНО**: относительный путь `"data.txt"` отсчитывается от **текущей рабочей
директории** процесса, а **НЕ** от расположения исполняемого файла или исходного кода.
Если программу запустить из другой директории (из IDE, из `build/`), файл не будет
найден. В тестах курса путь строится от исходного файла через макрос `__FILE__`.

### Режимы открытия файла <a id="fstream_modes"></a>

Вторым аргументом конструктора или метода `open()` передаётся режим открытия - 
набор флагов типа 
[`std::ios_base::openmode`](https://en.cppreference.com/w/cpp/io/ios_base/openmode.html),
которые объединяются оператором `|`:

- `std::ios::in` - открыть для чтения
- `std::ios::out` - открыть для записи
- `std::ios::trunc` - очистить существующий файл при открытии
- `std::ios::app` - перед **каждой** записью переходить в конец файла
- `std::ios::ate` - после открытия **один раз** перейти в конец файла
- `std::ios::binary` - бинарный режим (без преобразования символов перевода строки)
- `std::ios::noreplace` - ошибка, если файл уже существует (C++23)

Режимы по умолчанию:

- `std::ifstream` - `in`, флаг `in` добавляется всегда
- `std::ofstream` - `out`, флаг `out` добавляется всегда
- `std::fstream` - `in | out`, флаги **НЕ** добавляются

Файловый поток открывает файл так, как это сделала бы функция `fopen()` языка C.
Допустимые комбинации флагов перечислены в справке
[`std::basic_filebuf::open()`](https://en.cppreference.com/w/cpp/io/basic_filebuf/open.html),
флаг `ate` в ней **НЕ** учитывается. Любая другая комбинация - ошибка открытия.

| Флаги (без `binary`) | `fopen` | Нет файла | Файл есть |
|---|---|---|---|
| `out`, `out \| trunc` | `"w"` | создаётся | очищается |
| `out \| app`, `app` | `"a"` | создаётся | запись в конец |
| `in` | `"r"` | ошибка | чтение с начала |
| `in \| out` | `"r+"` | ошибка | чтение и запись с начала |
| `in \| out \| trunc` | `"w+"` | создаётся | очищается |
| `in \| out \| app`, `in \| app` | `"a+"` | создаётся | чтение, запись в конец |
| `out \| noreplace` (C++23) | `"wx"` | создаётся | ошибка |

- с флагом `binary` режим `fopen` получает букву `b`: `"rb"`, `"wb"`, `"r+b"` и т.д.
- в режиме `app` запись **всегда** идёт в конец файла, даже после `seekp`

Примеры:

```c++
std::ofstream log("log.txt", std::ios::app);                   // append to the end
std::fstream file("data.txt", std::ios::in | std::ios::out);   // edit existing file
std::ofstream image("image.bin", std::ios::binary);            // binary output
```

**ВАЖНО**: несколько неочевидных следствий таблицы:

- `std::ofstream` без флагов **очищает** существующий файл сразу при открытии, ещё
  до первой записи
- `std::ofstream("log.txt", std::ios::ate)` - это `out | ate`, то есть `"w"`:
  файл будет очищен. Чтобы дописывать в конец, нужен `app`, а чтобы открыть
  существующий файл и встать в конец с возможностью перемещаться - `in | out | ate`
- `std::fstream("data.txt")` - это `in | out`, то есть `"r+"`: если файла нет, он
  **НЕ** создаётся, открытие завершается ошибкой
- `in | trunc` без `out`, `trunc | app` - недопустимые комбинации, файл не откроется

### Чтение из файла <a id="fstream_read"></a>

Способы чтения:

- `in >> value` - форматированное чтение, пропускает пробельные символы
- `std::getline(in, line)` - строка до `'\n'`, сам `'\n'` извлекается и отбрасывается
- `std::getline(in, field, ';')` - строка до указанного разделителя
- `in.get(ch)` - один символ, включая пробельные
- `in.peek()` - посмотреть следующий символ, не извлекая его
- `in.read(buffer, count)` - `count` байт без форматирования (бинарные данные)
- `in.gcount()` - сколько символов извлекла последняя неформатированная операция
- `in.ignore(count, delim)` - пропустить символы

Правильные циклы чтения проверяют **результат** операции:

```c++
while (in >> x) {}                // values separated by whitespace
while (std::getline(in, line)) {} // line by line
while (in.get(ch)) {}             // char by char
```

После нормального завершения цикла установлены и `eofbit`, и `failbit`: последняя
попытка чтения не удалась, потому что данные закончились.

Пример кода построчного чтения и проверки, чем закончился цикл:

```c++
std::ifstream in(path);
std::string line;
int number = 0;
while (std::getline(in, line)) {
    std::cout << ++number << ": " << line << '\n';
}
if (in.bad()) {
    // read error (I/O error)
} else if (!in.eof()) {
    // stopped before the end of file (for >>: bad data)
}
```
- `in.bad()` - проверка на ошибку ввода-вывода
- `!in.eof()` - проверка остановки цикла на неверных данных

Часто необходимо произвести считывание файла заданного формата, например, в файле 
задается количество чисел, сами числа и строка текста:

```c++
std::ifstream in(path);
int count = 0;
in >> count;
std::vector<int> values;
if (count > 0) {
    values.reserve(count);
}
for (int i = 0, x = 0; i < count && in >> x; ++i) {
    values.push_back(x);
}
std::string line;
std::getline(in >> std::ws, line);   // skip '\n' after the last number
```

Прочитать весь файл в строку можно, скопировав буфер файла в строковый поток:

```c++
std::string ReadAll(const std::filesystem::path& path) {
    std::ifstream in(path);
    std::ostringstream buffer;
    buffer << in.rdbuf();       // copy the whole file
    return buffer.str();
}
```
- для `std::streambuf*` оператор `<<` копирует все символы из буфера до конца
- если файл пуст или не открылся, ничего не копируется, у `buffer` устанавливается
  `failbit`, а результат - пустая строка; поэтому открытие файла по-прежнему нужно
  проверять

### Запись в файл и буферизация <a id="fstream_write"></a>

Способы записи в файл:

- `out << value` - форматированный вывод, работают все манипуляторы
- `out.put(ch)` - один символ
- `out.write(buffer, count)` - `count` байт без форматирования

```c++
void WriteText(const std::filesystem::path& path) {
    std::ofstream out(path);   // create or truncate
    if (!out) {
        // throw std::runtime_error("cannot open " + path.string()); // exception
        return;
    }
    out << "10 20 30\n";
    out << "Hello, file!\n";
}                              // destructor: flush and close
```

Запись идёт через буфер: данные попадают в файл, когда буфер заполнится, при
`flush()` (или манипуляторах `std::flush`, `std::endl`), при `close()` и в
деструкторе. Поэтому:

- если тот же файл нужно прочитать другим потоком, пишущий поток надо сначала
  закрыть или сбросить его буфер `flush()`
- ошибка записи (например, закончилось место на диске) может обнаружиться только
  при сбросе буфера. Если результат важен, нужно явно вызвать `close()` и проверить
  состояние потока:

```c++
out.close();
if (!out) {
    // data was not written completely
}
```

Частый вызов `std::endl` в цикле записи в файл заметно замедляет программу, так как
каждый раз сбрасывает буфер. Для файлов используется `\n`.

### Позиционирование в файле <a id="fstream_seek"></a>

Поток хранит текущую позицию чтения и записи:

- `tellg()` - узнать позицию чтения (_get_)
- `seekg(pos)`, `seekg(offset, dir)` - перейти на позицию чтения (_get_)
- `tellp()` - узнать позицию записи (_put_)
- `seekp(pos)`, `seekp(offset, dir)` - перейти на позицию записи (_put_)

Направление `dir` типа `std::ios_base::seekdir`:

- `std::ios::beg` - от начала
- `std::ios::cur` - от текущей позиции
- `std::ios::end` - от конца

У файлового потока позиция одна на чтение и запись. Таким образом, `seekg` и `seekp`
двигают одну и ту же позицию. У строкового потока позиции раздельные.

Размер файла:

```c++
std::ifstream in(path, std::ios::binary);
in.seekg(0, std::ios::end);
const std::streamoff size = in.tellg();
in.seekg(0, std::ios::beg);
std::string data(static_cast<std::size_t>(size), '\0');
in.read(data.data(), size);
```
- проще узнать размер функцией `std::filesystem::file_size(path)` (C++17)

Чтение и перезапись в одном файле:

```c++
std::fstream file(path, std::ios::in | std::ios::out | std::ios::binary);
file.seekg(2);                     // absolute position
std::string word;
file >> word;
file.seekp(0);                     // switch to writing: seek first
file << "7";                       // overwrite the first byte
file.seekg(-6, std::ios::end);     // 6 bytes before the end
std::getline(file, word);
```
- при переходе от чтения к записи и обратно в потоке `std::fstream` нужно вызвать
  `seekg`, `seekp` (или `flush` после записи): ограничения те же, что у `FILE` в C
- запись **НЕ** вставляет данные, а перезаписывает байты, начиная с текущей позиции
- `tellg()` возвращает `-1`, если поток в состоянии ошибки

**ВАЖНО**: [`seekg`](https://en.cppreference.com/w/cpp/io/basic_istream/seekg.html) 
сбрасывает `eofbit` (C++11), но **НЕ** `failbit`. После цикла чтения до конца файла 
установлены оба флага, поэтому перед возвратом в начало нужен `clear()`:

```c++
while (std::getline(in, line)) { /* ... */ }
in.seekg(0);       // does nothing: failbit is set, tellg() == -1
in.clear();
in.seekg(0);       // ok
```

В текстовом режиме переходить можно только в начало, в конец или на позицию,
полученную ранее от `tellg`/`tellp`, как и для `fseek` в C. Произвольные смещения
корректны в бинарном режиме. В Linux режимы не различаются, но в Windows символ
`\n` в текстовом режиме хранится в файле как два байта `\r\n`.

### Бинарный режим <a id="fstream_binary"></a>

Флаг `std::ios::binary` отключает преобразование символов перевода строки и
ничего больше. Оператор `<<` в бинарном режиме по-прежнему пишет текст: число `18`
будет записано как два символа `1` и `8`.

Чтобы записать байты объекта, используются `write` и `read`, которые принимают
указатель на `char` и количество байт:

```c++
struct Point {
    std::int32_t x;
    std::int32_t y;
};
bool WritePoints(const std::filesystem::path& path, const std::vector<Point>& points) {
    std::ofstream out(path, std::ios::binary);
    if (!out) {
        return false; // cannot open file
    }
    const std::uint64_t count = points.size();
    out.write(reinterpret_cast<const char*>(&count), sizeof(count));
    out.write(reinterpret_cast<const char*>(points.data()),
        static_cast<std::streamsize>(count * sizeof(Point)));
    out.close(); // flush and check that data is written
    return static_cast<bool>(out);
}

std::vector<Point> ReadPoints(const std::filesystem::path& path) {
    std::ifstream in(path, std::ios::binary);
    if (!in) {
        return {}; // cannot open file
    }
    std::uint64_t count = 0;
    in.read(reinterpret_cast<char*>(&count), sizeof(count));
    const auto data_size = std::filesystem::file_size(path) - sizeof(count);
    if (!in || count != data_size / sizeof(Point)) {   // protects from huge count
        return {}; // broken file
    }
    std::vector<Point> points(count);
    in.read(reinterpret_cast<char*>(points.data()),
        static_cast<std::streamsize>(count * sizeof(Point)));
    if (!in) {
        return {}; // file is shorter than expected
    }
    return points;
}
```
- перед массивом записывается его размер, иначе при чтении неизвестно, сколько
  элементов ожидать
- `close()` с проверкой нужен потому, что ошибка записи может обнаружиться только
  при сбросе буфера
- количество из файла сверяется с размером файла: иначе повреждённый файл с 
  `count = 10^12` приведёт к попытке выделить терабайты памяти
- если байт меньше, чем запрошено, `read()` устанавливает `failbit`

Так можно записывать только _тривиально копируемые_ типы
(`std::is_trivially_copyable_v<T>`, C++17): их байты можно скопировать и получить
тот же объект. В код можно добавить проверку на этапе компиляции:

```c++
static_assert(std::is_trivially_copyable_v<Point>);
```

**НЕЛЬЗЯ** записывать так объекты с указателями, в том числе `std::string` и
`std::vector`, поскольку в файл попадёт адрес, а не данные, и после чтения указатель
будет висячим. Такие поля записывают по частям: размер, затем данные.

**ВАЖНО**. Бинарный файл, записанный таким образом, переносим только между
одинаковыми платформами:

- размер типов различается (`int`, `long`), поэтому используются типы
  фиксированного размера `std::int32_t`, `std::uint64_t`
- порядок байт (_endianness_) различается: x86 и ARM - little-endian, сетевой порядок -
  big-endian. Узнать порядок можно через `std::endian::native` (C++20, `<bit>`)
- в структуре могут быть байты выравнивания (_padding_), и их расположение
  зависит от компилятора

### Файловые потоки и RAII <a id="fstream_raii"></a>

Файловый поток владеет открытым файлом по идиоме RAII:

- файл открывается в конструкторе
- деструктор вызывает [`close()`](https://en.cppreference.com/w/cpp/io/basic_filebuf/close.html), который
  сбрасывает буфер и закрывает файл
- при выходе из функции, в том числе по исключению, файл гарантированно закрыт

При работе с файлом в языке C через `FILE*` каждый путь выхода из функции требует `fclose`.
В C++ закрытие происходит автоматически:

```c++
void Process(const std::filesystem::path& path) {
    std::ifstream file(path);
    if (!file) {
        return;
    }
    if (!Step(file)) {
        return;              // closed by destructor
    }
    ThrowException();        // closed during stack unwinding
}
```

Файловый поток **НЕ** копируется, но перемещается (C++11), поэтому его можно вернуть
из функции:

```c++
std::ofstream OpenLog(const std::filesystem::path& path) {
    std::ofstream log(path, std::ios::app);
    log << "--- log opened ---\n";
    return log; // move
}
```

Деструктор **НЕ** может сообщить об ошибке: если при закрытии возникла ошибка,
деструктор её проглотит. Поэтому явный `close()` нужен, когда:

- нужно проверить, что данные записаны полностью
- тем же объектом нужно открыть другой файл
- файл нужно освободить раньше конца области видимости (например, прочитать его
  другим потоком). Чаще проще ограничить время жизни потока блоком `{}`

### Типичные ошибки при работе с файлами <a id="fstream_pitfalls"></a>

1. Цикл `while (!in.eof())`:

```c++
std::ifstream in(path);   // file: "1 2 3\n"
int x = 0;
int sum = 0;
while (!in.eof()) {       // wrong
    in >> x;
    sum += x;
}
// sum = 9, not 6
```
- после чтения `3` в потоке остаётся `'\n'`, поэтому `eofbit` не установлен и цикл
  выполняется ещё раз: чтение неудачно, `x` не меняется, тройка прибавляется
  дважды. Если файл не открылся, `eofbit` никогда не установится и цикл станет
  бесконечным
- правильно: `while (in >> x) { sum += x; }`

2. Нет проверки открытия файла: при ошибке все операции молча ничего не делают

```c++
std::ifstream in("missing_file.txt");
int x = 0;
in >> x;   // nothing happens: x == 0, no error message
```

3. Относительный путь ищется от текущей рабочей директории, а не от исполняемого
   файла. Важно помнить при запуске из IDE или из `build/`.

```c++
std::ifstream in("data.txt");   // run from build/: looks for build/data.txt
```

4. `std::ofstream` очищает файл при открытии; для дозаписи нужен `std::ios::app`.

```c++
std::ofstream log("log.txt");                       // old content is lost
std::ofstream app_log("log.txt", std::ios::app);    // append to the end
```

5. `std::fstream` с режимом по умолчанию не создаёт файл.

```c++
std::fstream file("new.txt");    // in | out: fails if file does not exist
std::fstream created("new.txt", std::ios::in | std::ios::out | std::ios::trunc);
```

6. Чтение файла до сброса буфера записи.

```c++
std::ofstream out("data.txt");
out << 42;                // still in the buffer
std::ifstream in("data.txt");
int x = 0;
in >> x;                  // file is empty yet: x == 0
```
- перед чтением нужно вызвать `out.flush()` или `out.close()`, или ограничить время жизни
  `out` блоком `{}`
- в одном `std::fstream` между записью и чтением нужен `seekg(pos)`

7. Отсутствие `clear()` перед `seekg()` после чтения до конца.

```c++
while (std::getline(in, line)) { /* ... */ }
in.seekg(0);  // does nothing: failbit is still set
in.clear();   // reset state first
in.seekg(0);  // ok
```

8. Смешивание `>>` и `std::getline`.

```c++
// in contains "18\nIvan Ivanov\n"
int age = 0;
std::string name;
in >> age;                           // '\n' after 18 stays in the stream
std::getline(in, name);              // reads up to that '\n': name == ""
std::getline(in >> std::ws, name);   // name == "Ivan Ivanov"
```
- манипулятор `std::ws` пропускает все пробельные символы (пробелы, `\n`, `\t`)
  до первого непробельного
- если известен формат, можно также использовать метод `ignore()` для пропуска 
  символов после чтения с помощью `>>`

9. Запись `std::string` и других типов с указателями через `write`.

```c++
std::string name = "Ivan";
out.write(reinterpret_cast<const char*>(&name), sizeof(name));  // wrong
out.write(name.data(), name.size());                            // ok
```

## Строковые потоки `<sstream>` <a id="sstream"></a>

Строковый поток работает так же, как файловый, но вместо файла читает из строки
`std::string` и пишет в неё:

- `std::istringstream` - чтение из строки
- `std::ostringstream` - запись в строку
- `std::stringstream` - чтение и запись

Основные методы помимо методов потока:

- `str()` - получить копию содержимого
- `str(s)` - заменить содержимое строкой `s`
- `rdbuf()` - буфер `std::stringbuf`

Строковые потоки применяются для:

- сборки строки из значений разных типов с форматированием
- разбора строки на значения
- тестирования функций, которые принимают `std::istream&` или `std::ostream&`

### Поток вывода в строку `std::ostringstream` <a id="ostringstream"></a>

Часто поток вывода в строку используют для форматированного вывода:

```c++
std::string MakeLabel(const std::string& name, int id, double value) {
    std::ostringstream os;
    os << name << '#' << std::setw(3) << std::setfill('0') << id
       << " = " << std::fixed << std::setprecision(2) << value;
    return os.str();
}

MakeLabel("item", 7, 3.14159);   // "item#007 = 3.14"
```
- работают все манипуляторы, в отличие от `std::to_string`, у которой формат
  фиксирован (6 знаков после точки для `double`)
- настройки форматирования относятся к локальному потоку `os` и **НЕ** влияют на
  `std::cout`

### Поток ввода из строки `std::istringstream` <a id="istringstream"></a>

Разбор строки с числами:

```c++
std::vector<int> ParseInts(const std::string& line) {
    std::istringstream is(line);
    std::vector<int> result;
    int value = 0;
    while (is >> value) {
        result.push_back(value);
    }
    return result;
}
ParseInts("1 2 3 x 4");   // {1, 2, 3}: reading stops at "x"
```

### Двунаправленный поток `std::stringstream` <a id="stringstream"></a>

`std::stringstream` позволяет и писать, и читать. Позиции чтения и записи у него
раздельные.

При повторном использовании потока нужно и заменить содержимое, и сбросить состояние:

```c++
std::stringstream ss;
ss << "10";
int a = 0;
ss >> a;          // a = 10, eofbit is set
ss.str("20");     // replace content
ss.clear();       // reset state, otherwise next read fails
int b = 0;
ss >> b;          // b = 20
```
- `clear()` сбрасывает флаги, но **НЕ** очищает содержимое
- `str("")` очищает содержимое, но **НЕ** сбрасывает флаги
- проще и надёжнее создать новый поток в нужной области видимости

### Строковые потоки и пользовательские типы <a id="sstream_user_types"></a>

Оператор `>>` для своего типа устроен так же, как `<<`: принимает поток по ссылке и
возвращает его. При неверном формате оператор устанавливает `failbit`, как это
делают операторы стандартной библиотеки:

```c++
struct Point {
    int x = 0;
    int y = 0;
};
std::ostream& operator<<(std::ostream& os, const Point& p) {
    return os << '(' << p.x << ", " << p.y << ')';
}
// format "(x, y)"
std::istream& operator>>(std::istream& is, Point& p) {
    char open = 0, comma = 0, close = 0;
    Point tmp;
    if (is >> open >> tmp.x >> comma >> tmp.y >> close &&
        open == '(' && comma == ',' && close == ')') {
        p = tmp;                       // change p only on success
        return is;
    } 
    is.setstate(std::ios::failbit);
    return is;
}
```

Строковые потоки позволяют проверить такие операторы без консоли и файлов:

```c++
std::ostringstream out;
out << Point{1, -2};
assert(out.str() == "(1, -2)");

std::istringstream in("(3, 4) (5; 6)");
Point p;
in >> p;    // p = (3, 4), in is good
in >> p;    // p = (3, 4), in is fail
```

Если функция пишет прямо в `std::cout`, её вывод можно перехватить, подменив буфер
потока. Восстановить буфер нужно даже при исключении, поэтому подмену оформляют
как RAII-класс:

```c++
class CoutRedirect {
public:
    explicit CoutRedirect(std::streambuf* buffer) : old_(std::cout.rdbuf(buffer)) {}
    ~CoutRedirect() { std::cout.rdbuf(old_); }
    CoutRedirect(const CoutRedirect&) = delete;
    CoutRedirect& operator=(const CoutRedirect&) = delete;
private:
    std::streambuf* old_;
};

std::ostringstream captured;
{
    CoutRedirect redirect(captured.rdbuf());
    std::cout << "hidden";
}                                         // buffer restored
std::cout << captured.str() << '\n';      // hidden
```
- `rdbuf(new_buffer)` устанавливает новый буфер и возвращает старый
- без восстановления `std::cout` после уничтожения `captured` указывал бы на
  разрушенный буфер (UB)
